# F02 confirmatory N-body protocol

Status: **preregistered before generating or scoring the companion test corpora**.  F01 established
the algebraic and fixed-hyperparameter mechanism.  F02 asks whether spending ORBIT's saved local
linear-algebra budget on more neighbours improves trained predictive accuracy and calibration.  A
negative result narrows ORBIT to a numerical TERA backend; it must not be hidden by retuning on test
data.

## Questions and claim gates

F02 has two nested questions:

1. **Predictive mechanism:** does trained ORBIT under a TERA-`m=50` analytic prediction envelope beat
   TERA `m=50` on the same frozen data and with exactly the same learned kernel and noise parameters?
2. **Comparative performance:** does it also beat the released DSoftKI and DDSVGP implementations,
   plus a value-only local-GP control, on standardized scalar RMSE and, only where a common latent
   variance path is independently verified, predictive NLL?

Question 1 requires a paired reduction of at least 5% in standardized scalar RMSE and at least
`0.05` nat/test-point in NLL, with hierarchical 95% intervals excluding zero in the beneficial
direction.  Question 2 applies the RMSE threshold against every competing derivative-GP baseline;
the least favourable comparison controls the headline claim.  It applies the NLL threshold only to
baselines whose adapters expose and pass a regression test for common latent-function variance.
Method-native DDSVGP likelihood variance and DSoftKI's noise-floored covariance are never mixed with
TERA/ORBIT latent NLL as though they were the same quantity.  No method is called a calibrated
superior framework if it improves RMSE while materially worsening a verified common NLL, if any
dimension regresses by more than 2% RMSE or `0.02` NLL, or if task/provenance accounting is
incomplete.

## Frozen data design

Each corpus is generated by `data.generate_nbody_confirmatory`; one corpus is one fixed-mass
Hamiltonian and one independent experimental unit.  The exact grid is:

- particle counts `{2, 4, 6, 8, 10}` with three spatial dimensions, giving state dimensions
  `{12, 24, 36, 48, 60}`;
- 100 trajectories and 100 retained time points per trajectory (`dt=0.01`);
- deterministic 60/20/20 trajectory-group train/validation/test splits;
- generator seeds `mass=1729`, `trajectory=2718`, `split=31415`, and `validation=1618`;
- development replicas `{0, 1, 2}` and untouched confirmatory replicas
  `{101, 102, 103, 104, 105, 106, 107, 108, 109, 110}`.

All other generator fields remain the versioned defaults.  A replica number is mixed into every
random stream.  Replicas are never pooled into one GP because their fixed masses define different
functions.  Every NPZ, metadata sidecar, and SHA-256 manifest is frozen together.  The loader must
verify all three, use the stored group split, apply only the stored train-derived normalization, and
retain every row in the loaded corpus.

The predictive design then takes the same label-independent temporal slice for every arm.  Training
uses time indices
`{0,4,8,12,16,21,25,29,33,37,41,45,50,54,58,62,66,70,74,78,82,87,91,95,99}`
from every training trajectory (1,500 states).  Validation and test use
`{0,25,50,74,99}` from every respective trajectory (100 states each).  Selection is solely a frozen
function of stored `time_index`; it never inspects `E` or `F`, represents every trajectory, and
retains original source indices.  A secondary sensitivity may use ten evenly spaced time indices per
validation/test trajectory, but it cannot replace the primary slice.  Test labels from both
development and confirmatory corpora remain unscored until the recipe and candidate-neighbour
schedule below have been frozen from development validation data.

To bound dense-baseline tuning cost without selecting easy labels, optimizer-update selection uses
the preregistered validation subset `time_index={50}`: one state from each of the 20 validation
trajectories.  All three update candidates and optimizer seeds use exactly that subset.  After the
update count is selected, the selected recipe is rerun on the complete five-time validation slice;
the ORBIT neighbour schedule and all reported development-validation metrics use that complete
slice.  The one-time subset is a tuning device only and is never reported as the primary result.

## Arms and shared information

All gradient-capable methods receive the same raw states, scalar Hamiltonian values, full analytic
gradients, trajectory split, and temporal design slice.  The value-only conditioning ablation is
given the same states and values but not the gradient observations at prediction.  The primary
comparison consumes the saved canonical
arrays directly: baseline-owned unit-cube transforms, energy sign flips, and joint value-gradient
standardization are disabled.  In particular, the MD22 convention `y=-E`/`g=force` and DSoftKI's
released joint scaling are not reused for positive-Hamiltonian N-body data.  Predictions and
variances are reported in the canonical standardized target

\[
  x'=(x-x_{\min,train})/x_{\operatorname{span},train},\qquad
  y'=(H-\bar H_{train})/s_{H,train},\qquad
  \nabla_{x'}y'=\nabla_xH\,x_{\operatorname{span},train}/s_{H,train}.
\]

The arms are:

- **TERA-50:** released TERA training and dense local prediction with `m=50`;
- **ORBIT-50:** a same-neighbour numerical control using TERA-50's learned parameters;
- **ORBIT-resource:** exact-rank ORBIT with `m` selected from `{75, 100, 150, 200}` under the analytic
  TERA-50 prediction envelope below, using the same learned parameters as TERA-50;
- **DSoftKI-512:** released model/training code, 512 interpolation points and full gradients, but the
  common F02 data scale and optimizer-update budget;
- **DDSVGP-512:** released model/training code, 512 inducing points, with its unavoidable
  directional-gradient and single-noise parameterization disclosed explicitly;
- **value-only conditional ablation:** the same TERA-50 stationary scalar kernel, scalar noise,
  learned parameters, and neighbour set, but prediction conditions only on values.  Because its
  parameters came from TERA's derivative-informed fit, it isolates prediction-time gradient
  conditioning and is not presented as a separately trained value-only GP baseline.

The primary four-way kernel is isotropic RBF because released DDSVGP is RBF-only and forbids ARD.
Matérn-5/2 is a separately labelled TERA/ORBIT/DSoftKI sensitivity, not evidence from the four-way
comparison.  TERA hyperparameters are trained with its released minibatched Vecchia objective using
training neighbourhood size `m=20`; prediction `m` is varied only after fitting.  ORBIT does not get a
separate fit or test-dependent parameter adjustment.

The common optimizer-update candidates are `{20, 50, 100}`.  TERA uses that number of minibatch
updates directly with its released recipe batch size of 256.  DSoftKI and DDSVGP use batch size 1,024
on the 1,500-state design, so released epoch counts `{10, 25, 50}` give the same `{20, 50, 100}`
updates.  Each method gets the same three
configuration opportunities, selected globally using only the three development replicas'
validation metrics on the preregistered one-time tuning subset.  Released-recipe preprocessing and
a resource-matched inducing/neighbour curve are reported as contextual sensitivities, not blended
into the primary ranking.  Optimizer seeds `{11, 29, 47}` are paired across methods; seed-level
metrics are averaged within a corpus before replica-level inference.  The external runners must also
seed Python's `random` module because DDSVGP samples derivative coordinates through it.  No true
test dataset is passed into any training routine, and all in-training evaluation/logging is
disabled.  No test metric participates in model, update-count, or resource selection.

For each independently trained method, choose the update count with the lowest macro-average
standardized scalar RMSE on that tuning subset, weighting state dimensions and fixed-mass replicas
equally after averaging its three optimizer seeds; an exact tie goes to fewer updates.  TERA-50
determines the one shared TERA/ORBIT/value-only-conditional fit budget.  DSoftKI and DDSVGP each
select their own budget by the same rule.  NLL is not used for this selection because the external
variance semantics are not assumed comparable.

This is optimizer-update matching, not sample-exposure, epoch, FLOP, or wall-time matching.  TERA's
three candidates draw `{5,120, 12,800, 25,600}` Vecchia target factors with replacement; the external
loaders traverse `{15,000, 37,500, 75,000}` states, including each epoch's short final batch.  Every
result therefore records batch size, realized update count, target factors or states processed,
training wall time, and peak accelerator allocation.  The last two are descriptive and are not used
as inferential resource matches.

For the ORBIT-versus-TERA scalar NLL gate, both methods supply their matched latent Gaussian variance
in canonical standardized units.  External methods enter that NLL comparison only after their
adapters expose a common latent-function variance and pass an independent small-fixture regression;
otherwise their native NLL remains secondary.  Observation variance, including learned/fixed scalar
noise exactly once, is separately named.  Latent variance and the noise term are logged independently
so incompatible variance semantics cannot be concealed by one number.  Invalid, nonfinite, or
nonpositive raw variances are failures, not clipped successes.

## Analytic resource rule

Resource matching is local prediction work, because ORBIT and TERA share one TERA fit.  Per target,
the TERA-50 reference materializes `50^4 = 6,250,000` reduced-covariance elements and has leading
dense-Cholesky count `50^6/3`.  For every ORBIT validation prediction, record exact rank, iterations,
recomputed residual, operator-core elements, structured-operator FLOPs, and preconditioner FLOPs.

An ORBIT `m` is eligible in a state dimension only if:

1. every development-validation solve converges at freshly recomputed relative residual `<=1e-5`;
2. every un-clipped raw variance is finite and positive;
3. its maximum operator-core state proxy is no larger than `50^4`; and
4. the upper 95% bootstrap endpoint of mean counted operator-plus-preconditioner FLOPs per target is
   no larger than `50^6/3`.

Among eligible values, select the lowest mean validation NLL subject to validation RMSE being within
1% of the best eligible RMSE; break remaining ties in favour of smaller `m`.  This produces one frozen
`m` per state dimension.  Accelerator memory and isolated-node wall time are descriptive only and do
not override this rule.  Training costs for every arm are reported separately.

## Metrics and uncertainty

Primary metrics for ORBIT versus TERA are standardized scalar RMSE and mean Gaussian latent NLL in
nat/test-point, with equal trajectory weight.  Standardized scalar RMSE is the all-arm headline
metric; common latent NLL becomes an all-arm metric only for independently verified variance paths.
Secondary diagnostics are raw-energy RMSE, method-native and observation NLL, empirical 50/90/95%
interval coverage, variance validity, solve residuals, analytic resource counts, peak accelerator
allocation, and isolated-node wall time.  Gradient RMSE is secondary and reported only where a
released method exposes a well-defined gradient prediction; it cannot substitute for either primary
scalar metric.  Raw gradient predictions are rescored centrally as physical-unit per-coordinate
RMSE.  Released `d_rmse` values, which instead measure RMS Euclidean norm per state, remain separately
named and are never merged with it.

Metrics are first computed per held-out trajectory, preserving its five selected, correlated time
points as a group.  Within each sampled dimension, trajectory MSE is averaged before taking the RMSE
square root.  Paired uncertainty uses a hierarchical nonparametric bootstrap that resamples replica
blocks, then state dimensions within replicas, then held-out trajectories within each corpus.  The
primary resampling unit for between-task generalization is the fixed-mass replica, not an individual
state.
Use 10,000 bootstrap draws and seed `20260803`.  Report paired absolute NLL changes and both absolute
and relative RMSE changes.  Dimension-specific paired intervals are reported alongside the pooled
interval; a pooled win cannot hide a material dimension regression.

## Controls and failure policy

- ORBIT-50 must agree with TERA-50 within the float32 solver resolution; F01's separate float64 result,
  not this tolerance, supports the exact-equivalence claim.
- The value-only conditional ablation tests whether gradient observations add information to the
  local predictive conditional after holding TERA's derivative-informed parameters fixed; it does
  not test a fully independent value-only training pipeline.
- A deterministic permutation-null arm shuffles training gradients between source rows without
  changing values or inputs.  It is run on development data only and must degrade if the credited
  derivative signal is real.
- Preconditioning is ablated on a development subset.  It may improve resource counts, but converged
  posterior quality should not change beyond solver tolerance.
- Any ORBIT test solve above its freshly recomputed residual tolerance, any non-exact basis in an
  `ORBIT-exact` arm, or any nonfinite/nonpositive raw variance fails the predictive gate rather than
  removing a row.
- Missing tasks, hash/config mismatches, trajectory overlap, unregistered temporal selection,
  convergence failures, invalid variance, OOM, and timeout all remain visible in task accounting.
  No failed unit is silently dropped from a positive claim, and an all-replica comparison never
  switches post hoc to successful complete cases.

The confirmatory recipe consists of the committed source tree, dependency lock, submodule commit,
this protocol, generated-data SHA manifests, selected training configuration, and selected
dimension-to-`m` schedule.  The final test runner must record hashes for all of them before it reads
test arrays.  Wall-clock comparisons run only on exclusive Slurm allocations.
